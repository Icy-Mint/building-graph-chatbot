01

Why this comparison

A mechanical or building-systems team rarely has one dataset. They have a pile of disconnected time-series: zone temperature and humidity off the BMS, CO₂/air quality from IAQ sensors, whole-building and sub-metered energy, a utility or weather feed, sometimes a carbon-intensity signal layered on top — each on its own cadence, some live, some only historical, a few with a forecast bolted on. None of that is the hard part. The hard part is that no one on the facilities team can ask it anything: "which zone is running hot right now," "has this AHU been short-cycling this week," "where's our decarbonization headroom" each mean opening three dashboards, exporting a CSV, and doing the join by hand.

This project is a small, deliberately scaled-down slice of that problem: link a fraction of it — a building graph (rooms, AC units) plus sensor time-series (temperature, occupancy) — and put a chatbot on top, so a building management team could pull live or historical conditions on demand, build a report from the answer, or catch an emerging fault ahead of the service ticket. The dorm stands in for a small building portfolio; temperature and occupancy stand in for the fuller mechanical stack (temp/humidity/air-quality/energy/carbon, live or predicted). What doesn't shrink with the demo is the architecture decision underneath it — every team doing this for real ends up choosing between the same three shapes, usually on instinct rather than evidence:

chatbot_classifier.py
Classify the question into a fixed list of intents, then run hand-written Cypher or pandas for that intent. Nothing is generated at query time.
chatbot_nl2cypher.py
Let the model write the Cypher itself for every question (LangChain's GraphCypherQAChain), validated against the schema before it runs.
tool-calling-agent
Give the model seven typed, pre-written tools and let it call them in a loop. It never writes a query itself — only picks tools and arguments.

How each one actually works

Each one is a real, reasonable choice, and each is usually defended with the same anecdotes: fixed taxonomies are "fast and cheap but brittle," text-to-query is "flexible but unsafe," agents are "robust but slow and expensive." Those claims are directionally true and almost never measured. This project holds the model, the database, and the questions constant and measures what actually happens: not just how often each one is right, but how each one is wrong — because for a facilities team deciding whether to trust a chatbot's answer in a report, the failure shape matters more than the failure rate.

The building itself is synthetic but not arbitrary: a 2-floor dorm wing with 6 dorm rooms and 2 mechanical rooms, 2 AC units each serving 3 rooms, temperature + occupancy sensors on a 5-minute cadence for 14 days — 48,384 readings generated from a deterministic model (sinusoidal temperature profiles, hour-of-day occupancy probabilities) so every ground-truth answer below can be checked exactly, including against the generator that produced the data. Standing in for temperature/humidity/air-quality/energy/carbon lets the comparison stay checkable end to end; nothing about the three architectures depends on which sensor types are behind them.
02

Method

All three systems ran against the same local Neo4j + TimescaleDB instance and the same model (claude-sonnet-5, thinking disabled for predictable tool calls), so differences in the results trace back to architecture, not to data or model drift. Ground truth for every question was computed independently with raw SQL / Cypher against the database before any system was asked anything.

Model
claude-sonnet-5, identical config
Database
1 shared local Neo4j + TimescaleDB
Questions
107, 17 categories, programmatically generated
Grading
automated checks against independently-computed ground truth

The 17 categories span direct lookups (current/all-time temperature extremes, occupancy status, AC-to-room mapping), harder shapes (multi-room comparisons, historical occupancy rate, next-hour occupancy forecast), compound questions that need two facts joined in one answer, and 12 deliberately out-of-scope questions (weather, trivia, "book me a parking spot") to see whether each system knows what it doesn't know.

A methodology correction, made before publishing: the first automated pass scored chatbot_classifier.py at 79/107. Reading the actual failing answers showed 12 of those were a grading bug, not a real failure — e.g. asked "are both room 101 and 104 occupied?", chatbot_classifier.py correctly reported both rooms' status but never used the literal word "both," which the checker required. The checker was fixed to accept any answer that gets the underlying facts right regardless of phrasing, and all 107×3 answers were re-graded from the saved transcripts — no new model calls, same underlying data. Final score: 91/107. The corrected categories are called out below rather than silently folded in.
Two model quirks noticed along the way, not architecture findings: first, claude-sonnet-5 prepended a stray, literal cypher word on its own line before the actual query in 57 of 129 raw Cypher-generation calls checked across both runs (~44%) — despite the prompt explicitly saying "no prefixes, no code fences." Verified harmless: the chain stores the cleaned query internally before execution (checked intermediate_steps directly), so it never caused a wrong answer here, but it would matter for any Cypher-execution path without that cleanup. Second, chatbot_nl2cypher.py's occupancy_forecast score (2/8, in the table below) isn't only the "no decline path" finding this page leads with — some of those misses are a genuine capability limit: correctly writing a multi-level time-aggregation query (group by hour-of-day, average, across a date range) in one shot is harder for the model than a direct lookup, a separate problem from whether it can say "I don't know."

Headline accuracy is a near-tie — 83–86% across all three — which makes it the least interesting number on this page. Cost and latency are not close: tool-calling-agent used roughly 48× the input tokens of chatbot_classifier.py and ran 5.6× slower on average, because its multi-turn tool loop resends the growing conversation (including large tool-result payloads) on every iteration, instead of one classify-then-query shot. At an estimated $3 / $15 per million input/output tokens (Anthropic's exact current rate couldn't be independently confirmed at the time of writing), that's roughly $0.003 per question for chatbot_classifier.py versus roughly $0.11 per question for tool-calling-agent — about 33× more expensive per answer.

chatbot_classifier.py — a fixed taxonomy has no "other"
Q: “Does room 201 have any sensors?”
“I don't have access to the specific building layout or sensor data for room 201 in this conversation. No information has been provided to me about this building's configuration…”
This is false — the data exists and the bot is connected to it. There's just no classifier category for "room metadata," so the question falls into the fallback chain, which hallucinates a plausible-sounding reason it can't help instead of admitting the real one: it was never coded to look. The same gap explains compound and alltime_occupancy_rate — any question shaped unlike the ~10 intents it was built for just isn't answerable, no matter how simple it actually is.
chatbot_nl2cypher.py — no path to "I don't know"
Q: “What's the weather like outside today?”
“Cannot answer with the current schema.”
— emitted as the literal text of a Cypher query, which then fails with a raw Neo4j syntax error shown straight to the user.
Text-to-Cypher has no decline mechanism: when the model can't express the answer as a query, it tries to write English as a query, which the database rejects. That's 0/12 on out-of-scope questions — every single one — and the same mechanism breaks occupancy_forecast (2/8), where expressing "average occupancy at this hour-of-day across two weeks" in one Cypher query is past what the model reliably generates. Everywhere a direct query can reach, though, this was the most precise of the three — 100% on every lookup, comparison, and even compound two-fact questions, because Cypher joins naturally handle "and also give me X."
tool-calling-agent — honest about gaps, imprecise under a row cap
Q: “What's the lowest temperature ever recorded in room 101?” (true answer: 16.36°C, Jan 14 04:20)
“…the lowest hourly-average temperature recorded was approximately 17.76°C, occurring at 2024-01-12 03:00 UTC.”
Off by 1.4°C and the wrong day. The agent's tools return raw 5-minute readings only up to a 2,000-row cap, so for a 14-day, all-rooms question it reaches for hourly averages instead — which smooths away the single sharpest dip the question actually asked for. The same tool set also has no function that finds a minimum across all rooms at once (only get_hot_periods, which checks above a threshold), so for the building-wide version of this question it said plainly: “I don't have a tool that directly finds an all-time minimum across all rooms in one call…” and asked a clarifying question rather than guessing. That's the one failure mode worth calling a feature: of the three systems, this is the only one that reliably says "I don't know" instead of inventing an answer (11/12 on out-of-scope questions, and never once a hallucinated building fact anywhere in 107 questions).
04

Which one would you actually ship

Not "which one wins" — each one wins a different deployment. For a facilities team, that maps roughly onto how the chatbot gets used: a kiosk answering the same handful of questions all day, an internal tool for engineers who can shrug off an occasional error screen, or a report-facing assistant where a hallucinated number is the one failure that can't be tolerated. The honest read of 107 questions:

Pick chatbot_classifier.py when…

the set of questions is small and known in advance, latency and cost matter (lobby kiosk, SMS bot, anything called at volume), and you can live with a hard wall around what it answers. 33× cheaper and 5.6× faster than the agent for the questions it was built to handle — but a new question shape means a code change, not a prompt tweak, and it will confidently claim "no data" for things it actually has.

Pick chatbot_nl2cypher.py when…

questions are varied but still fundamentally database lookups, an internal/trusted audience can tolerate an occasional raw error screen, and you need the model to combine facts in ways you didn't anticipate (it was the only system to get every single compound and comparison question right). Put a guardrail in front of it for anything open-ended — it has no idea when a question is outside its domain.

Pick tool-calling-agent when…

the audience is external or non-technical, a hallucinated answer is worse than a slow one, and the question set will keep growing. It degrades the most gracefully by far and handles genuinely novel, multi-step questions — at roughly 33× the cost per answer and real latency (9+ seconds average), and only as good as the tools you remembered to build (no minimum-finding tool here meant a systematic, fixable gap, not a one-off mistake).

05

What's next

Two different directions, not one — closing the cost/latency gap this page measured, and testing all three architectures against data that isn't designed to be clean.

Make the agent cheaper, not just document it
Two concrete, unbuilt fixes, not things already tried and found insufficient: extend Anthropic's prompt caching across the growing tool-call conversation itself (today only the system prompt + tool list are cached; every tool result gets re-sent at full price on every later turn, which is the actual driver of the 48× token gap) and build the cheap/capable model router that was planned but never implemented — every question currently gets claude-sonnet-5 regardless of how trivial it is.
Test against real building data
This database is a deliberately small, deterministic stand-in so every ground-truth answer could be checked exactly. The natural next step is pointing the same three architectures at a real source: a building management system (BMS) export or live API, a sensor manufacturer's cloud API, or a managed IoT platform (AWS IoT Core, Azure IoT Hub / Digital Twins) streaming live telemetry. That surfaces what this demo can't: real sensor dropouts and data gaps, auth/rate-limits on the data side, multi-building schemas nobody hand-designed to be clean, and whether typed-tool and NL-to-Cypher still hold up once the graph isn't tidy. The MCP server below is the piece that makes swapping in that real source possible without touching the agent.
06

Added since this ran: an MCP server

tool-calling-agent grew a Model Context Protocol server (mcp_server/) over the same 7 typed tools this page's results are based on. It changes nothing measured above — same functions, same validation, same read-only enforcement, just a second, standardized way to reach them — so it's worth being specific about what it actually buys, what it costs, and why it was built at all.

Capability
Any MCP-compatible client — Claude Desktop, another agent framework, an IDE — can now call these building tools with no custom integration code; the protocol is the interface, not a bespoke API. The SDK auto-derives each tool's JSON schema from its Python type hints and auto-coerces arguments (ISO date strings, lists) into what the functions expect — verified live against the real database — so the 7 tool functions themselves needed zero changes to gain this.
Tradeoff
A second schema-derivation path is a second place for drift to creep in: the drift-guard test added for the eval harness checks the Anthropic-tool-use schemas against the real function signatures, but doesn't yet check the MCP server's auto-derived ones against that same source of truth. It also pulls in a surprising amount of infrastructure (starlette, uvicorn, cryptography) for what's currently a stdio-only use case, and ships with no auth or rate limiting — fine for a trusted local client, not yet for anything broader.
Where it actually matters
Not in this project, where it's the same process serving the same synthetic data either way. MCP's real value shows up when the backend changes and the agent shouldn't have to: the same agent loop could point at a real BMS (Niagara/Tridium, Honeywell, Siemens Desigo), a sensor manufacturer's cloud API, or AWS IoT Core / Azure IoT Hub, by writing a new MCP server against that API — zero changes to the agent, since it only ever speaks MCP, never a specific vendor's SDK. That's the actual on-ramp for the "test against real building data" item to the left.

Scope and limitations: one model (claude-sonnet-5), one synthetic 14-day dataset, one grading pass per answer (automated keyword/number matching against ground truth, with one documented correction made after reading actual failing transcripts — not a substitute for human review at larger scale). Token-based cost estimates exclude Anthropic's prompt-cache read/write pricing, which would lower tool-calling-agent's real-dollar disadvantage somewhat, though not by enough to close a 48× gap in raw tokens.
